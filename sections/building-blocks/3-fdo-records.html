FDO records

This section specifies how an FDO record is implemented by Handle-based FDOs.
Handle record
Each Handle record consists of a list of Handle values. Each Handle value is represented as a JSON object with (at least) five types (see also [[Handle Technical Manual]]):
  • index (integer)
  • type (string)
  • data (object)
  • ttl (the time-to-live in seconds of the value, an integer (or, in the rare case of an absolute expiration time, that expiration time as an ISO8601-formatted string))
  • timestamp (an ISO8601-formatted string)
FDO record
The conceptional FDO record (according to the [[FDO specification]]) consists of attributes (tuples)
a1=(k1:v1), a2=(k2:v2), ..., an=(kn:vn). Each attribute ai belongs to one of two types:
  1. ai instantiates an attribute definition, which is identified by a PID, has an attribute name, and a cardinality. Some of the ai may even instantiate the same attribute definition (this depends on the cardinality of the attribute definition: a cardinality of x..y allows this attribute definition to be instantiates in a record between x and y times). ki is either the PID or the name of the attribute definition. vi must be a value that is valid against the attribute definition.
  2. Or ai is a simple combination of an attribute name and a value. In this case, ki is the attribute name, and vi is the attribute value. vi does not need to comply to any validation rules.
[H3-1] Mapping the FDO Record to the Handle Record

We assume an FDO record which consists of FDO attributes (tuples) a1=(k1:v1), a2=(k2:v2), ..., an=(kn:vn). The attributes are reordered such that a1, ..., ak instantiate attribute definitions, and ak+1, ..., an are simple names plus values, 1≤k≤n-1. Mapping the FDO record to a Handle record means to map all FDO attributes a1, ..., an to a list of Handle values h1, ..., hm (m≤n) as follows:

We start by mapping a1, ..., ak to handle values: Let A1,...,Ar be all attribute definitions that are instantiated by at least one of a1, ..., ak, with r the total number of instantiated attribute definitions. It holds r≤k because some attributes may instantiate the same attribute definitions. Define the sets S1, ..., Sr. The attributes a1, ..., ak are placed in S1, ..., Sr depending on which attribute definition they instantiate. In more detail, ai is placed in Sj if ki is either the name or the PID of Aj. Now, each set Sj is mapped to handle values. There are two allowed ways how to do this:

  1. One handle value is created which contains all attributes that are placed in Sj. The handle value looks as follows:
    • index: any positive integer that was not yet used by any other handle value
    • type: either the name or the PID of attribute definition Aj
    • data.value: a list containing all values of the attributes placed in Sj
  2. |Sj| handle values are created, each containing one of the attributes that are placed in Sj. The handle values look as follows:
    • index: any positive integer that was not yet used by any other handle value
    • type: either the name or the PID of attribute definition Aj
    • data.value: the value of one of the attributes placed in Sj

We continue by mapping ak+1,...,an to handle values:

Let s be the total number of mutually different attribute names ki in ak+1,...,an. It holds s≤n-k-1 because some attributes may have the same attribute name. Define the sets T1, ..., Ts. The attributes ak+1, ..., an are placed in T1, ..., Ts depending on their attribute name. In more detail, ai is placed in Tj if ki is the name belonging to Tj. Now, each set Tj is mapped to handle values. Again, there are two allowed ways how to do this:

  1. One handle value is created which contains all attributes that are placed in Tj. The handle value looks as follows:
    • index: any positive integer that was not yet used by any other handle value
    • type: the attribute name kj
    • data.value: a list containing all values of the attributes placed in Tj
  2. |Tj| handle values are created, each containing one of the attributes that are placed in Tj. The handle values look as follows:
    • index: any positive integer that was not yet used by any other handle value
    • type: the attribute name kj
    • data.value: the value of one of the attributes placed in Tj
    Note that attributes whose name is `HS_ADMIN` MUST be mapped this way.
The remaining properties of Handle values are usually set according to their default values, but possibly also with different values, if this makes sense in the given context:
  • data.format: string (and data.format: admin for attributes with the name `HS_ADMIN`)
  • ttl: 86400
  • timestamp: [current time]

Even though the mapping allows some freedom, it is recommended to be consistent within the same FDO:
  • You should consistently either use only the names or the PIDs of an attribute definition as the `type` in the handle value.
  • Also, you should decide either to map your attributes with higher cardinalities to one handle value with a list of values, or to multiple individual handle values with single value, within your FDO.
[H3-2] Mapping the Handle Record to the FDO Record
This mapping is the exact reverse operation from what was described in [H3-1]. Mapping a Handle record with Handle values h1,...,hn to an FDO record with attributes a1,...,am means to map each Handle value hi to one or several FDO attributes. The Handle value hi with
  • index: any integer
  • type:name or attribute PID
  • data.format: string
  • data.value: single value, or list of values
  • ttl: 86400
  • timestamp: 2025-05-06T12:30:44Z
is mapped to FDO attributes ai1 = (ki1, vi1), ..., air = (kir, vir) as follows:
  1. The index, data.format:, ttl, and timestamp are dropped.
  2. If data.value is a list of r elements, then this handle value is mapped to r attributes ai1, ..., air. If data.value is a single value, it is mapped to a single attribute.
  3. For each of the resulting FDO attributes, ki is either the name of the attribute, or the PID of attribute definition that is instantiated.
