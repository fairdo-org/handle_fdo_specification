FDO records

This section specifies how an FDO record is implemented by Handle-based FDOs.
Handle record
Each Handle record consists of a list of Handle values. Each Handle value is represented as a JSON object with (at least) five types (see also [[Handle Technical Manual]]):
  • index (integer)
  • type (string)
  • data (object)
  • ttl (the time-to-live in seconds of the value, an integer (or, in the rare case of an absolute expiration time, that expiration time as an ISO8601-formatted string))
  • timestamp (an ISO8601-formatted string)
FDO record
The conceptional FDO record (according to the [[FDO specification]]) consists of a set of attributes a1, a2, ..., an. Each attribute belongs to one of three types:
  1. ai=(Ai,vi), with Ai being an FDO attribute definition that is listed in at least one of the profiles of this FDO. Ai is identified by a conceptual PID (denoted 0.FDO/...), it has an attribute name as well as a cardinality. vi must be a value that is valid against Ai.
  2. ai=(Ai,vi), with Ai being an attribute definition that is NOT listed in any of the profiles of this FDO. The same conditions on Ai and vi apply as in 1.
  3. ai=(si,vi). Here, si is a simple attribute name in form of a string. vi does not need to comply to any validation rules.
Some of the attributes ai in the conceptional FDO record may refer to the same attribute definition Ai. This depends on the cardinality of the attribute definition: A cardinality of x..y allows this attribute definition to be instantiated in a record between x and y times. Simple attribute names si (see 3.) can be repeated as often as desired, as they do not specify any cardinality.
[H3-1] Mapping the FDO Record to the Handle Record

We assume an FDO record which consists of FDO attributes a1, a2, ..., an. The attributes are reordered such that

  1. a1, ..., ak instantiate attribute definitions that are listed in the profile,
  2. ak+1, ..., al instantiate attribute definitions that are not listed in the profile, and
  3. al+1, ..., an are simple names with values,

1≤k≤l≤n-1. Mapping the FDO record to a Handle record means to map all FDO attributes a1, ..., an to a list of Handle values h1, ..., hm (m≤n) as follows:

  1. We start by mapping a1, ..., ak to handle values: Let A1,...,Ar be all attribute definitions that are instantiated by at least one of a1, ..., ak and that are in at least one of the profiles, with r the total number of mutually different instantiated attribute definitions. It holds r≤k because some attributes may instantiate the same attribute definition. Define the sets S1, ..., Sr. The attributes a1, ..., ak are placed in S1, ..., Sr depending on which attribute definition they instantiate. Now, each set Sj is mapped to handle values. There are two allowed ways how to do this:
    1. One handle value is created which contains all attributes that are placed in Sj. The handle value looks as follows:
      • index: any positive integer that was not yet used by any other handle value
      • type: either the name or the PID of attribute definition Aj
        • If the attribute definition PID is used, the conceptional PID from the conceptional FDO record (denoted 0.FDO/...) is replaced by a handle-based representation of this conceptional PID.
        • Using the attribute name is only allowed if there are no other attribute definitions with the same name in the FDO record.
      • data.value: a list containing all values of the attributes placed in Sj
    2. |Sj| handle values are created, each containing one of the attributes that are placed in Sj. The handle values look as follows:
      • index, type: same as above (see a.).
      • data.value: the value of one of the attributes placed in Sj
    If you want to use human-readable attribute names of attribute definitions (instead of attribute definition PIDs) as the type in a handle value, it is essential that these attribute definitions are part of at least one of the profiles of this FDO. Through the profile, a machine can map the attribute name to an attribute PID and access the attribute definition. Without being part of a profile, there would be no way to find the attribute definition belonging to the attribute name.
  2. We continue by mapping ak+1,...,al to handle values: This mapping works exactly the same as the mapping for the a1,...,ak (see 1.), except that all types in the handle values MUST be PIDs of attribute definitions (not attribute names).
  3. Finally, al+1,...,an are mapped to handle values. This mapping works again the same for the a1,...,ak (see 1.), except that all types in the handle values MUST be attribute names (in fact, al+1,...,an do note have any no associated PIDs or attribute definitions). Note that attributes whose name is `HS_ADMIN` or `URL` MUST be mapped to individual handle values to guarantee that administration and resolution of handles works as intended.
The remaining properties of Handle values are usually set according to their default values, but are also allowed to contain different values, if this makes sense in the given context:
  • data.format: string (and data.format: admin for attributes with the name `HS_ADMIN`)
  • ttl: 86400
  • timestamp: [current time]
Even though the mapping allows some freedom, it is recommended to be consistent within the same FDO:
  • For the attributes that instantiate attribute definitions in the profile, you should consistently either use only the names or the PIDs of an attribute definition as the `type` in the handle value.
  • Also, you should decide either to map your attributes with higher cardinalities to one handle value with a list of values, or to multiple individual handle values with single value, within your FDO.

[H3-2] Mapping the Handle Record to the FDO Record
This mapping is the exact reverse operation from what was described in [H3-1]. Mapping a Handle record with Handle values h1,...,hm to an FDO record with attributes a1,...,an (m≤n) means to map each Handle value hi to one or several FDO attributes. The Handle value hi with
  • index: any integer
  • type: attribute name or attribute PID
  • data.format: string
  • data.value: single value, or list of values
  • ttl: 86400
  • timestamp: 2025-05-06T12:30:44Z
is mapped to an FDO attribute / multiple FDO attributes as follows:
  1. The index, data.format, ttl, and timestamp are dropped.
  2. The data.value field is inspected. If data.value is a list of r elements, then this handle value is mapped to r FDO attributes by creating one attribute for each list element. If data.value is a single value, it is mapped to a single attribute.
  3. The type field and the FDO profile are inspected to decide which category of FDO attributes (1., 2. oder 3.) this handle value belongs to. In case of 1., if the attribute name is used as the type, the attribute PID can be recovered through the profile. Handle representations of these attribute PIDs are mapped to conceptional PIDs.
