FDO profiles

[H4-1] Representation of FDO Profiles
The Handle record of a Handle-based FDO profile must contain a fixed, predefined set of FDO attributes (see Table 3). Note that there are two types of FDO attributes in the Handle record:
  1. Meta information about the profile, to describe the FDO profile itself: 21.T11969/Type, 21.T11969/Profile, 21.T11969/Name (all mandatory), 21.T11969/Description (optional).
  2. The actual content of the profile, from which validation rules (for FDOs instantiating this profile) can be derived: 21.T11969/Data, 21.T11969/JsonSchema, 21.T11969/Attribute, 21.T11969/Extends, and 21.T11969/denyAdditionalAttributes. There are two equivalent ways how to define the validation rules, see [H4-1a] and [H4-1b].
Table 3: The list of attribute definitions which MUST be used when defining a new Handle-based FDO profile. This table does not include all information about the attribute definitions. For more information, please resolve the attribute definition PIDs via the Handle System.
PID of the attribute definition Attribute value Cardinality of the attribute
21.T11969/Type The string FDO_Profile. Additional types may be added, if applicable. 1..*
21.T11969/Profile The string 21.T11969/ProfileDef. Additional profiles may be added, if applicable. 1..*
21.T11969/Name Human-readable and localized label(s) for the profile. 1..*
21.T11969/Description Human-readable and localized description(s) for the profile. 0..*
21.T11969/Data Either the string 21.T11969/JsonSchema (way 1) or the string Not_Applicable (way 2). If both ways are combined, it has the value of way 1. 1
21.T11969/JsonSchema This attribute is just used when the profile is represented according to way 1. In this case, it is a URL pointing to a JSON schema. 0..1
21.T11969/Attribute This attribute is just used when the attribute is represented according to way 2. The attribute 0.FDO/Attribute defines the list of attribute definitions that MUST be instantiated in any FDO using this profile. The attribute 0.FDO/Attribute is repeated once for each attribute definition that should be in the profile. 0..*
21.T11969/Extends This attribute is just used when the attribute is represented according to way 2. If this profile is an extension of another profile, the value of this attribute specifies the PID of the parent profile. 0..*
21.T11969/denyAdditionalAttributes This attribute is just used when the attribute is represented according to way 2. The value is an optional boolean flag indicating whether an FDO that instantiates the respective profile MUST NOT have additional attributes than those given by the profile. This restriction is only active if the value is set to a truthy boolean. 0..1

[H4-1a] Profiles implemented by JSON Schemas

The FDO record of the profile links to a JSON schema which contains all validation rules of the profile.
  • The linking is done by using the attribute 21.T11969/Data. This attribute applies attribute referencing to point to the attribute 21.T11969/JsonSchema, which has as its value a JSON schema.
  • The JSON schema stacks together attribute definitions using the `allof` JSON Schema keyword. The referenced attribute definitions carry their own cardinalities. Those cardinalities can be overwritten (i.e. narrowed down, e.g. from 0..10 to 1..5) in the JSON Schema to adapt the attributes to the new context. The JSON schema must at least contain the mandatory attributes 21.T11969/Type, 21.T11969/Profile, and 21.T11969/Data.
  • A FDO profile may specify that it extends another FDO profile by using the JSON schema $ref keyword to reference the JSON schema of a parent profile (see [H4-4a] for details).
  • The FDO profile may also specify whether it allows instantiating FDOs to contain additional FDO attributes (see example below for details).
The Handle record of a profile that is constructed according to [H4-1a] could look as follows:
PID of Attribute Definition Example Value
21.T11969/Type FDO_Profile
21.T11969/Profile 21.T11969/ProfileDef
21.T11969/Name my-simple-profile
21.T11969/Description A very small profile for illustration purposes.
21.T11969/Data 21.T11969/JsonSchema
21.T11969/JsonSchema 
{"$ref": "https://raw.githubusercontent.com/fairdo-org/handle_fdo_specification/refs/heads/main/json-schema/%5BH4-1%5D_Profile/ProfileDef_simple.json"}
Profile FDO record (fictionary PID: 21.example/profile01)
The full validation schema for this profile can be found here. The validation schema is constructed as follows:
  • line 3: identifier of the profile definition
  • line 4: name of the profile
  • line 5: description of the profile
  • line 8-23: the attribute definitions used by this profile are stacked together
  • lines 24-113: the cardinality of `21.T11969/Name` attribute is narrowed down to 1-2 (instead of 1-5 in the original profile). The concrete lines containing the new cardinalities are 41-42 and 101-102. The `21.T11969/Name` attribute is now allowed to be instantiated 1-2 times in the handle record.

This schema validates any handle record that has 1-n profiles, 1-10 URLs, 1-2 names, 1-n data references and potentially additional attributes that are not listed in the profile. An example record that validates against this schema is this record.

To prevent the FDO record from containing additional attributes, this JSON snippet can be added into the JSON schema (i.e., into the `allof` using the `$ref` keyword). Then, any handle values that carry other attributes will cause a JSON schema validation error.

Services such as the Data Type Registry [will] implement the profile-, attribute- and JSON schema-generation such that this complexity is hidden from the user.

[H4-1b] Profiles implemented on Handle-record level

The FDO profile is fully specified in the Handle record, simply relying on references to other attributes, potential profile extension and a boolean. In more detail:
  • The attribute 21.T11969/Attribute defines the list of attribute definitions that MUST be instantiated in any FDO instantiating this profile. In case that no extension is used, the attribute 21.T11969/Attribute MUST be repeated at least three times, once with each of the values 21.T11969/Type, 21.T11969/Profile, 21.T11969/Data, because these are the mandatory attributes that MUST be contained in any FDO. Additional attributes can be added by further repeating the 21.T11969/Attribute with other values.
  • If this profile is an extension of another profile, the value of the attribute 21.T11969/Extends specifies the PID of the parent profile (see [H4-4b]).
  • The attribute 21.T11969/denyAdditionalAttributes is an optional boolean flag indicating whether an FDO that instantiates the respective profile MUST NOT have additional attributes than those given by the profile. This restriction is only active if the value is set to a truthy boolean.
  • The mandatory attribute 21.T11969/Data is set to Not_Applicable.
The same profile as in looks like this when it is represented using [H4-1b]:
PID of Attribute Definition Example Value
21.T11969/Type FDO_Profile
21.T11969/Profile 21.T11969/ProfileDef
21.T11969/Name my-simple-profile
21.T11969/Description A very small profile for illustration purposes.
21.T11969/Data Not_Applicable
21.T11969/Attribute 21.T11969/Profile
21.T11969/Attribute 21.T11969/Data
21.T11969/Attribute 21.T11969/URL
21.T11969/Attribute 21.T11969/Name
21.T11969/denyAdditionalAttributes False
Profile FDO record (fictionary PID: 21.example/profile01)

An implementation of an FDO validator would be able to validate the profile `21.example/profile01` against this example Handle record example record.

Both ways [H4-1a] and [H4-1b] of defining profiles can be combined by using all attributes 21.T11969/Data, 21.T11969/JsonSchema, 21.T11969/Attribute, 21.T11969/Extends, and 21.T11969/denyAdditionalAttributes simultaneously. In this case, when creating or updating this FDO profile, it must be checked that both ways induce the same validation rules.
[H4-2] Profile Definition Profile
The Handle-based profile definition profile has the PID 21.T11969/ProfileDef and is the Handle-based implementation of Table 3. It uses both mechanisms [H4-1a] and [H4-1b] to encode its validation rules.
[H4-3] Root Profile
The Handle-based root profile has the PID 21.T11969/Root. It uses both mechanisms [H4-1a] and [H4-1b] to encode its validation rules. It can be used as a parent profile for profile extension.
[H4-4] FDO Profiles Extension Mechanism
Handle-based FDOs implement profile extension in two different but equivalent ways, see [H4-4a] and [H4-4b].
Profiles that prohibit the use of additional attributes that are not listed in the profile cannot be extended.

[H4-4a] Profile extension implemented by JSON Schemas

An FDO profile constructed as JSON Schema (see [H4-1a]) embeds a parent JSON schema from a parent FDO profile through the keyword `$ref`. Additional attributes can be added with the `allof` keyword. The cardinality of all newly added attributes can be overwritten (i.e., narrowed down) in the profile extension.
We take the profile from and extend it with the additional attribute full name:
PID of Attribute Definition Example Value
21.T11969/Type FDO_Profile
21.T11969/Profile 21.T11969/ProfileDef
21.T11969/Name my-simple-profile-extended
21.T11969/Description A very small profile for illustration purposes. It extends `21.example/profile01`.
21.T11969/Data 21.T11969/JsonSchema
21.T11969/JsonSchema 
{"$ref": "https://raw.githubusercontent.com/fairdo-org/handle_fdo_specification/refs/heads/main/json-schema/%5BH4-4%5D_Profile_Extension/ProfileDef_Extension.json"}
Profile FDO record (fictionary PID: 21.example/profile02)
The full validation schema for this profile can be found here. The validation schema is constructed as follows:
  • line 3: identifier of the profile definition
  • line 4: name of the profile
  • line 5: description of the profile
  • line 6: the profile contains all properties from the parent schema
  • line 8-11: additional attribute definitions that extend the parent profile can be added
  • lines 12-101: the cardinality of `21.T11969/Full_Name` attribute is narrowed down to 1 (instead of 0-2 in the original attribute definition). The concrete lines containing the new cardinalities are 29-30 and 89-90. The `21.T11969/Name` attribute must be instantiated exactly once in the handle record.

This schema validates any handle record that has 1-n profiles, 1-10 URLs, 1-2 names, 1-n data references, 1 full name and potentially additional attributes that are not listed in the profile. An example record that validates against this schema is this record.

To prevent the FDO record from using additional attributes, this JSON snippet can be added into the JSON schema (i.e., into the `allof` using the `$ref` keyword). Then, any handle values that carry other attributes will cause a JSON schema validation error.

[H4-4b] Profile extension implemented on handle record-level

An FDO profile constructed on Handle record level references a parent FDO profile using the attribute 21.T11969/Extends. Its value must be a PID pointing to another FDO profile.
The same profile as in looks like this when it is represented using [H4-1b] in combination with extension:
PID of Attribute Definition Example Value
21.T11969/Type FDO_Profile
21.T11969/Profile 21.T11969/ProfileDef
21.T11969/Name my-simple-profile-extended
21.T11969/Description A very small profile for illustration purposes. It extends `21.example/profile01`.
21.T11969/Data Not_Applicable
21.T11969/Attribute 21.T11969/Full_Name
21.T11969/Extends 21.example/profile01
21.T11969/denyAdditionalAttributes False
Profile FDO record (fictionary PID: 21.example/profile02)
